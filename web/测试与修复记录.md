## 3. 代码风格与架构核查

本次没有把 Controller 直接连到 JPA，也没有把业务判断塞进前端。现有调用方向仍为：

```text
Controller → AiLearnOrchestrator → 领域 Service → Store SPI → JPA Adapter
```

- 分页通过既有 Facade、Service 和 Store 端口传递，数据库实现仍封装在 Repository 适配器中。
- 类似题生成作为独立的 `PracticeGenerationService` 加入，没有修改批改规则、评分器或原有 AI 助手职责。
- `ErrorSeverity` 是明确的领域枚举，归档时生成，查询时过滤；没有在 Controller 中复制严重程度规则。
- AI 错题工具使用按请求创建的绑定工具，不在单例 Bean 中保存用户状态，也不信任模型提供用户 ID。
- `AiAssistantController` 已按项目常用格式整理为显式导入、标准缩进和短方法。

结论：本次确实扩展了若干端口方法，但没有形成反向依赖或跨层调用；不属于为了修复而大面积破坏 OCP。后续若继续增加多种错题筛选条件，可在 Repository 适配器内部改用 Specification，避免派生查询组合继续增长。

## 4. 安全核查

### 已修复

1. **AI 工具越权读取**：原工具把 `ownerUserId` 暴露为模型参数，提示词注入可能诱导模型查询其他用户。现在用户 ID 由认证上下文取得并在服务端绑定，模型工具不再接收用户 ID。
2. **敏感账号修改缺少复验**：修改邮箱或密码现在必须提供当前密码；错误时返回 403，不会把普通输错密码误判为 Token 失效。
3. **模型输入输出边界**：类似题请求限制错误分类、语言和文本长度；模型响应限制题目数量及标题、描述、代码模板长度。
4. **认证状态码**：未认证统一返回 401，403 保留给已认证但无权访问的情况。
5. **数据完整性**：V8 迁移增加数据库外键，避免继续产生孤立的提交和错题记录。

### 部署前仍需处理

- 生产环境必须显式设置强随机 `JWT_SECRET`、数据库密码和 `DEEPSEEK_APIKEY`，不能使用仓库中的本地默认值。
- 登录、AI 对话和 AI 出题尚未配置限流；面向公网前应在网关或反向代理增加频率限制。
- `npm audit --omit=dev` 报告 ECharts 5.x 存在 1 项中等级 XSS 公告；自动修复要求升级到 ECharts 6.1，属于破坏性主版本升级。本次未使用 `--force` 冒险升级，后续应在独立分支升级并目视回归全部图表、Tooltip 和富文本配置。
- 删除账号接口沿用原设计，只要求有效 JWT；若正式开放 UI，建议增加当前密码确认或二次确认。
- V8 外键迁移会校验历史数据。部署前必须备份数据库并检查孤立记录，不能在唯一生产库上直接试跑。
- 默认测试不连接真实 MySQL、Flyway 和 DeepSeek，不能替代部署环境联调。
